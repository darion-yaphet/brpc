# 第 8 周：综合实验、一次小改进与最终复盘

[返回总计划](learning-plan.md) · [上一周：可观测性与性能](07-observability-and-performance.md)

本周安排 **7.5 小时，分 5 次完成**。将前七周的实验整理成“可观测的双实例 Echo 实验台”，并完成一项范围明确、有证据的小改进。本文是待执行计划；不代表综合项目、测试或性能结果已经完成。

## 1. 开始条件与最终交付

开始前应具备：第 2 周的学习副本、第 3/4 周的 RPC 收发图、第 5 周的调度笔记、第 6 周的故障实验，以及第 7 周的指标和压测基线。如果某项缺失，优先补齐一个最小版本，再增加新功能。

本周沿用 `example/learning_echo_c++/` 与 `build/learning-lab/`。框架及其测试构建在 `build/learning/`。计划中的新增接口由前几周的练习实现，不能拿原始 `echo_server` 直接运行自定义参数。

最终交付四类材料：

| 材料 | 建议位置 | 应包含的内容 |
| --- | --- | --- |
| 实验使用说明 | `example/learning_echo_c++/README.md` | 构建、启动、参数、正常与失败示例、停止方式 |
| 实验代码 | `example/learning_echo_c++/` | 可控延迟/失败、路由参数、调用生命周期、业务指标 |
| 验证记录 | `notes/records/week-08.md`，原始输出放 `build/learning-records/week-08/` | 环境、配置、矩阵、测试结果、结论与限制 |
| 小改进 | 本次选题涉及的少量文件 | 问题说明、改动、验证、适用边界 |

实验台本身可以是本地练习；面向项目的小改进应单独描述范围，避免把整套学习记录混成一个难以评审的改动。

### 单元 1：固定实验接口，明确成功条件

先检查前几周已经实现的行为。缺失项在学习副本中补齐，不给框架核心增加学习专用开关。

| 程序 | 接口 | 约定与检查点 |
| --- | --- | --- |
| 服务端 | `--listen_addr` | 两个实例使用 `127.0.0.1:8000`、`127.0.0.1:8001` |
| 服务端 | 学习新增 `--study_delay_ms` | 默认 0；非负毫秒数，通过 bthread 友好的等待注入业务延迟 |
| 服务端 | 学习新增 `--study_fail` | 默认 false；启用后使用明确的业务失败分支，记录具体错误码 |
| 客户端 | `--server`、`--load_balancer` | 支持 list/file 命名和 rr；地址写入实际使用的 Channel 初始化参数 |
| 客户端 | `--timeout_ms`、`--max_retry` | 记录有效值，不将 Channel 默认值与 Controller 覆盖值混淆 |
| 客户端 | 学习新增 `--study_request_count` | 沿用第 2 周的有限次数参数，显式设置每组调用数，结束前等待回调完成 |
| 客户端 | 学习新增 `--study_backup_request_ms` | 默认 -1；赋给 `ChannelOptions::backup_request_ms`，实验时与重试预算一起设置 |
| 指标 | 请求/失败计数与处理耗时 | 记录暴露名称、单位、计数位置、时间范围 |
| 生命周期 | 一次终结、状态回收 | 正常、业务失败、超时及停止时都有明确的清理路径 |

前几周若采用了别的等价接口，可以保留，但应先同步 README 与运行命令。所有 `study_*` 参数都是练习扩展，框架和原始 Echo 并不自动提供。

源码核对入口：[原始 Echo server](../example/echo_c++/server.cpp)、[原始 Echo client](../example/echo_c++/client.cpp)、[ChannelOptions](../src/brpc/channel.h)、[Controller](../src/brpc/controller.h)、[默认重试策略](../src/brpc/retry_policy.cpp)。特别检查业务失败码是否属于默认重试集合；例如选择 `EINVAL` 与选择某个连接错误码会带来不同实验语义。

在笔记中先写下面的预测表，运行后再填实测列：

| 场景 | 输入/配置 | 预期需要验证的行为 | 实测证据 |
| --- | --- | --- | --- |
| 正常 | 两端无延迟、无失败 | 每次调用成功，响应正确 | 待填写 |
| 业务失败 | 单实例 `study_fail=true` | 客户端可见业务错误，done 和资源完成清理 | 待填写 |
| 确定性慢响应 | 单实例延迟 200ms，RPC 超时 50ms，重试 0 | 客户端超时；服务端稍后完成不应造成第二次客户端完成 | 待填写 |
| 实例退出 | 双实例 rr，运行中停止一个实例 | 记录失败窗口、健康后端的服务情况及恢复过程 | 待填写 |
| 备份请求 | 一快一慢，backup 20ms，deadline 500ms，重试预算 1 | 测量尾延迟与执行量，不预设每次都会触发备份或一定改善 | 待填写 |

### 单元 2：整合与启动双实例

首先让学习副本在正常配置下构建成功，再逐项开启故障。沿用第 2 周的平台配置；如果更换了编译器、依赖或 brpc 构建目录，应重新配置学习副本，而不是继续链接旧库。

```bash
mkdir -p notes/records build/learning-records/week-08
cmake --build build/learning-lab --parallel 4
cmake --build build/learning --target rpc_press --parallel 6
```

**以下启动命令以学习副本已实现上述自定义参数为前提。** 每个服务占一个终端，各自 Ctrl-C 退出。先确认 8000/8001 未被之前的实验占用。

终端 A，快实例：

```bash
./build/learning-lab/echo_server \
  --listen_addr=127.0.0.1:8000 \
  --study_delay_ms=0 \
  --study_fail=false \
  --enable_rpcz=true \
  --rpcz_database_dir=build/learning-records/week-08/rpcz-8000
```

终端 B，慢实例：

```bash
./build/learning-lab/echo_server \
  --listen_addr=127.0.0.1:8001 \
  --study_delay_ms=200 \
  --study_fail=false \
  --enable_rpcz=true \
  --rpcz_database_dir=build/learning-records/week-08/rpcz-8001
```

两个进程使用不同 rpcz 数据目录。该参数来自 [span.cpp](../src/brpc/span.cpp)，启用开关见 [rpcz_service.cpp](../src/brpc/builtin/rpcz_service.cpp)。目录独立也方便将两个实例的追踪记录与请求计数区分。

终端 C，先观察没有备份请求时的分布：

```bash
./build/learning-lab/echo_client \
  --server='list://127.0.0.1:8000,127.0.0.1:8001' \
  --load_balancer=rr \
  --timeout_ms=500 \
  --max_retry=1 \
  --study_request_count=100 \
  --interval_ms=10 \
  --study_backup_request_ms=-1
```

记录这 100 次调用后，将 backup 改为 `--study_backup_request_ms=20` 再运行。这个小样本先验证功能与计数；稳定尾延迟结论仍需第 7 周的更充分采样。若此前更改了第 2 周的有限次数客户端，先恢复相同契约，再比较两组实际完成的逻辑调用数。不要按 wall clock 时长相同就假定逻辑调用数相同。

每次变更只调整一个变量。客户端停止发起后等待在途处理结束，再抓取两个服务端的计数；仍有在途调用时就标注截断，不能把未完成请求当成消失。

### 单元 3：跑完矩阵，解释结果

按“正常 → 单实例业务失败 → 单实例超时 → 双实例退出 → 备份请求”的顺序执行单元 1 的矩阵。业务失败和超时实验可复用第二个实例，重新启动时改变其参数；实例退出只停止自己运行的实验进程。

对于确定性超时，直接访问慢实例，防止 rr 选到快实例混淆结论：

```bash
./build/learning-lab/echo_client \
  --server=127.0.0.1:8001 \
  --timeout_ms=50 \
  --max_retry=0 \
  --study_request_count=3 \
  --interval_ms=20 \
  --study_backup_request_ms=-1
```

这里客户端超时不等于服务端业务已停止。对照 [OnVersionedRPCReturned / EndRPC](../src/brpc/controller.cpp) 和 [ProcessRpcResponse](../src/brpc/policy/baidu_rpc_protocol.cpp)，说明迟到响应为何不能再完成一次已结束的逻辑调用。

每个场景至少填入以下信息：

| 记录项 | 口径 |
| --- | --- |
| 配置 | 客户端、两个服务端、构建类型、Git revision |
| 调用 | 发起数、成功数、失败数、错误码分布、结束时仍在途数 |
| 业务执行 | 两个服务端在统计窗口内进入业务方法的次数，使用增量 |
| 延迟 | 客户端端到端和服务端处理耗时分开；说明是否只统计成功调用 |
| 路由 | 成功响应的远端实例；失败时地址信息可能不完整 |
| 追踪 | 至少一条 rpcz 时间线与对应逻辑请求的关联依据 |

计算 `失败率 = 失败调用数 / 已完成逻辑调用数`。另记录 `服务端总执行次数 / 逻辑调用数` 作为**业务执行放大比**；它不是所有网络发送尝试的精确计数，因为有些尝试可能未到达业务方法。注意计数窗口、预热流量、在途请求和实例重启会影响分母与分子。

用于普通流量基线的有限时长命令如下。`rpc_press` 使用 `--lb_policy`，学习 Echo 客户端使用 `--load_balancer`，两者不要混用：

```bash
./build/learning/output/bin/rpc_press \
  --proto=example/learning_echo_c++/echo.proto \
  --method=example.EchoService.Echo \
  --server='list://127.0.0.1:8000,127.0.0.1:8001' \
  --lb_policy=rr \
  --input='{"message":"week08"}' \
  --qps=50 \
  --duration=30 \
  --timeout_ms=500 \
  --max_retry=0 \
  --dummy_port=8888
```

参数来源：[rpc_press.cpp](../tools/rpc_press/rpc_press.cpp)。该工具当前没有上述学习专用 backup 开关；备份请求对照仍由学习客户端完成。测性能时沿用 [第 7 周](07-observability-and-performance.md) 的预热、重复和窗口规则。

最终报告至少给出两个有证据的结论。例如：“在这组延迟分布和请求量下，备份请求改变了成功请求的尾延迟，但服务端执行量上升”，或者“未观察到稳定改善”。每个结论附配置与观测，不把一次运行推广成普遍性能结论。

### 单元 4：选择并完成一项小改进

阅读 [贡献指南](../CONTRIBUTING.md)，选一个已被前七周证据支持的目标。优先使用现有模块和测试结构。

| 选题 | 适用情况 | 最小交付 | 验证方式 |
| --- | --- | --- | --- |
| 文档示例 | 发现某个用法容易误解，当前说明不足 | 一段准确说明及可执行示例 | 执行示例，核对对象生命周期与结果 |
| 行为测试 | 重要边界只有口头解释，缺少直接覆盖 | 一个有意义的测试和它验证的契约 | 测试能实际运行；检查不会因过滤错名字而空跑 |
| 小型修复 | 已存在稳定复现的问题 | 最小修复与回归测试 | 原版本失败，修改后通过，再跑相关模块测试 |

先用五句话写明：问题是什么、触发条件、预期行为、当前证据、准备修改哪些文件。无法给出证据时，选文档或测试改进，不人为制造一个“框架 bug”作为作业。

若修改实现，按以下顺序执行：

1. 找到最接近的已有用例，明确准备、触发、断言、清理。
2. 建立失败复现；只补测试而不修 bug 时，则说明新增覆盖的独立价值。
3. 修改最小范围，不顺手重构无关模块。
4. 运行新用例及相关已有用例，确认实际运行数与结果。
5. 根据影响范围补构建/模块测试；文档或练习代码变更不需要为凑数量跑全仓库测试。

可用于回归对照的既有测试：

```bash
cmake --build build/learning \
  --target brpc_channel_unittest brpc_server_unittest --parallel 6
(
  cd build/learning/test
  ./brpc_channel_unittest --gtest_filter='ChannelTest.success:ChannelTest.timeout:ChannelTest.retry:ChannelTest.backup_request'
  ./brpc_server_unittest --gtest_filter='ServerTest.serving_requests'
)
```

检查每个测试命令的退出状态与摘要，前一个失败不能因后一个通过而被忽略。以上是原框架行为基线，**不能自动证明学习副本的新业务分支正确**；副本仍需自己的正常、失败、超时和结束时资源回收验证。新测试的名字在实际编写后填入记录，不预先冒充现有测试。

最后检查 diff、空白问题和非预期产物：

```bash
git status --short
git diff --stat
git diff --check
```

`git diff` 默认不展示未跟踪文件的内容；README 或实验源文件如为新文件，要单独打开审阅。只整理本次选题的改动，保留工作区中的其他工作。

### 单元 5：完成交接说明与讲解

让使用说明包含八项内容：环境、构建、参数表、双实例启动、客户端运行、三种基础场景、指标/追踪入口、停止与清理。用新终端从头执行一遍，任何需要额外解释的步骤都补进 README。

进行 15 分钟闭卷讲解：

1. **3 分钟：API。** 谁创建 Channel/Controller/Service，异步状态活到何时？
2. **4 分钟：链路。** 从 Stub 到序列化、Socket、输入处理、业务 done，再到客户端完成。
3. **3 分钟：机制。** IOBuf 如何管理数据，bthread 如何等待和唤醒？
4. **3 分钟：证据。** 展示一个失败或性能现象、对应配置和源码解释。
5. **2 分钟：改进。** 展示小改进的触发条件、diff、验证及仍存在的限制。

对下面的问题各写一段回答，每段附一个源码或实验引用：

- 为什么同步调用的易用性与底层并发机制不矛盾？
- 为什么客户端只拿到一个响应，服务端可能执行多次？
- 为什么 IOBuf 共享存储不等于所有数据操作都没有复制？
- 为什么业务处理时间短，客户端 p99 仍可能高？
- 如果明天换一种协议，哪些通用层仍可复用，哪些回调需要改变？

## 3. 最终验收

- [ ] 正常、业务失败、确定性超时、实例退出、备份请求五类场景均有完整配置和观测。
- [ ] 客户端成功/失败/在途统计与服务端计数的时间范围明确，逻辑调用和物理尝试没有混为一谈。
- [ ] 至少一条 rpcz 追踪可以与本人的调用图相互解释。
- [ ] 自己编写或改动的异步代码有明确的结束与回收条件，失败分支也验证过。
- [ ] 有一项范围清楚的小改进，验证与改动类型匹配，未运行的检查明确列出。
- [ ] 新终端能按 README 完整演示并停止实验，实验端口和数据库目录互不冲突。
- [ ] 能完成 15 分钟讲解；说不清的地方已列入后续问题，而非用术语略过。

不要求本周覆盖所有协议、写新调度器或提交上游 PR。达到验收标准后，主线结束。
